# Instamart Customer Intelligence & Support Copilot

## 1. Project Overview

This project implements a customer intelligence and support copilot using synthetic Instamart-style data. It covers data auditing and cleaning, SQLite storage, SQL and pandas analytics, customer segmentation, lapse prediction, privacy-first ticket triage, policy retrieval, and a database-backed refund agent.

All generated records are synthetic. The project uses an offline mock LLM and local files; it does not require a hosted LLM, API key, or network call. The refund workflow is a simulation and does not perform real financial transactions.

### Project capabilities

1. Read and audit CSV exports.
2. Clean data and persist trusted tables in SQLite.
3. Write SQL queries and pandas analytics.
4. Segment customers and train a leakage-aware lapse prediction model.
5. Redact PII and triage support tickets with retries and output validation.
6. Retrieve policy passages and execute bounded, database-backed agent tools.
7. Apply token, time, iteration, checkpoint, and duplicate-refund guardrails.

## 4. Data-Fetching and Data-Quality Workflow

This exercise intentionally uses local synthetic CSV files. For example:

```python
pd.read_csv("data/raw/orders.csv", keep_default_na=False)
```

In a production project, a fetch function might download from an approved endpoint or query a data warehouse. This exercise uses local synthetic data and has no credentials.

Recommended workflow:

1. Inspect shape, data types, null and blank counts, duplicate rows, keys, and impossible values before cleaning.
2. Apply one documented cleaning rule at a time.
3. Compare row counts and value distributions before and after each cleaning step.
4. Write clean CSVs for inspection and SQLite tables for repeatable SQL queries.
5. Run assertions before downstream analytics and modelling. A failed assertion should stop the pipeline rather than silently propagate invalid data.

### Leakage safeguards and limitations

- No orders dated September 1, 2025 or later are used to construct lapse-model input features.
- September activity is used only to generate the lapse target label.
- Segment labels are not used as lapse-model input features.
- Imputers, scalers, and encoders are fitted using training data within the model pipeline and cross-validation process.
- Random oversampling is applied only to training data. The original test set remains unchanged.
- The Premium retention flag is calculated from whole-window RFM data, which includes the September target period. It is therefore a post-hoc label.
- Consequently, the Premium retention list is illustrative and is not a leakage-free evaluation of a production retention strategy.
- The model and retention list use synthetic project data and should not be treated as production customer predictions.

## 7. Part C - Support Ticket Triage and Privacy Guardrails

### Implementation Summary

Part C implements a privacy-aware support ticket triage pipeline in `src/triage.py`. The pipeline processes all 164 tickets while preserving their original input order.

### 1. Input Guardrails

- Empty or whitespace-only tickets are marked `skipped_empty`.
- Tickets with an estimated token count above 400 are marked `flagged_long`.
- Four empty tickets and four long tickets were identified.
- The four long tickets had an estimated length of 734 tokens.
- These tickets are excluded from model calls.

### 2. Personal Information Redaction

Personal information is redacted before ticket content is sent to the model. The patterns are applied in the required order:

1. Email addresses -> `[EMAIL]`
2. Phone numbers -> `[PHONE]`
3. Order IDs -> `[ORDER_ID]`

| Redaction type | Replacements |
|---|---:|
| Email addresses | 55 |
| Phone numbers | 91 |
| Order IDs | 132 |

### 4. Retry Handling

Every model call is protected by retry handling:

- Maximum of three retries.
- Base delay: 0.05 seconds.
- Exponential backoff with jitter: `BASE_DELAY * 2**n * random.uniform(0.9, 1.15)`.
- Each retry is logged with the ticket ID, retry number, and wait duration.
- `mock_llm.reset()` is called immediately before each complete pipeline run.

Each full run encountered 19 transient failures, and all were recovered through retries. The observed retry waits were approximately 0.0453 to 0.0562 seconds.

### Refund policy and tool workflow

The refund tools are backed by SQLite order lookup and Python business rules:

- Only completed orders are eligible for a late-delivery refund.
- A completed order delivered in more than 45 minutes qualifies for a full refund of the order amount.
- A completed order delivered in 45 minutes or less does not qualify for a late-delivery refund.
- Refunds up to INR 1,000 are approved automatically by the simulation.
- Refunds above INR 1,000 are escalated to a human support lead.
- Cancelled orders are not refunded because they were never charged.

The agent uses a bounded tool loop and records tool steps and run results. It supports checkpoint creation and crash recovery, plus maximum-iteration, token, and time limits.

### ReAct vs Plan-and-Execute

This project uses **ReAct (Reasoning and Acting)** for the refund and customer-support agent.

**ReAct approach**
- The agent alternates between reasoning, selecting a tool, observing its result, and deciding the next action.
- It retrieves order details, searches refund policies, calculates the eligible refund, and then issues a refund or escalates the case.
- Tool execution is checkpointed, allowing the agent to resume after an interruption.
- Decisions can adapt to actual tool responses.

**Plan-and-Execute approach**
- The agent first creates a complete plan containing the required steps.
- A separate execution phase follows that plan.
- It is useful for complex workflows with predictable steps and multiple dependent tasks.
- Unexpected results may require the original plan to be revised.

**Why ReAct was selected**

Refund decisions depend on order status, delivery time, policy, and order amount. ReAct allows the agent to observe each tool result before choosing the next action. This supports denied refunds, missing orders, high-value refunds requiring escalation, and unexpected situations.

**Limitations**

ReAct may require multiple model calls and consume more tokens. Repeated tool calls and loops must be controlled using maximum iterations, token limits, time limits, and checkpoint-based recovery.

## 9. Limitations and Future Improvements

- All customer, order, and ticket data are synthetic.
- The offline mock model is a deterministic simulation, not a hosted language model.
- The refund ledger is a local JSONL audit trail, not a real transaction or payment system.
- The retention list is illustrative and should not be treated as a production targeting model.
- ReAct can consume multiple model calls and tokens; safety limits are required.
- The duplicate-refund check is suitable as a capstone demonstration, but production requires atomic idempotency enforcement.
- Production work would add authentication, authorization, secure secret management, monitoring, schema contracts, data lineage, model drift checks, access controls, and human approval workflows.
- Compare outputs with the supplied capstone brief and investigate differences rather than hardcoding expected answers.
- The Premium retention list uses a whole-window RFM label that includes the target period; it is illustrative and not a leakage-free evaluation.
- Oversampling increases lapse recall at the cost of lower precision, so retention campaigns require an appropriate review capacity and business threshold.
